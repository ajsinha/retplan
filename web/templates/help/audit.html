The audit is a list of checks run against your plan and its fixed-return projection every time you open it. It exists so that you never have to take a number on trust.

Blocking and Review

  • Blocking checks fail as FAIL. They mean the model is internally inconsistent or the inputs are impossible. The dashboard shows a red banner while any of them fails; do not rely on any figure until it clears.
  • Review checks fail as REVIEW. The model still works, but an input is outside the range most people would defend. It may be deliberate; make sure it is.

The header pill summarises: the number of blocking failures, else the number to review, else “all checks pass”.

The roll-forward identity

This is the important one. For every year of the projection it checks

closing = (opening − withdrawals − forced draws + paid in − fees) × (1 + return)

to a relative tolerance of one part in a million. The engine computes balances account by account and asset by asset; this check rebuilds the total from the reported flows alone. If a flow was dropped, counted twice, or taken from the wrong place, the two disagree and the check fails — regardless of how the numbers were produced.

{% call note('why', 'What it does not prove') %}

The return in the identity is inferred from the balances themselves, so the check proves that every flow is accounted for, not that the return is right. Whether your return assumptions are sensible is what the Review checks, and the “what you are actually assuming” panel on the dashboard, are for. The check also runs on the fixed-return projection only, not on every simulated trial.

When something fails

{% call steps() %}
  • Read the Detail column; it often names the account or regime.
  • Fix the input on the page the check names — most failures are a typo or a row that does not add to 100%. {{ goto('plan_section', 'Open accounts', 'accounts') }} {{ goto('plan_section', 'Open markets', 'markets') }}
  • Save, and reopen the audit: it re-runs on every visit.
  • If the roll-forward or negative-balance check fails with sensible inputs, export the plan as JSON and report it: that is a fault in the engine, not in your plan.
    • {% endcall %} {% call note('trap', 'Make regime rows add to exactly 100%') %}

    The market engine refuses a transition row that does not add to 100% almost exactly, and it does so before the audit gets to run — so a bad row usually shows up as an error page on the dashboard and the audit rather than as a failed check here. Type the diagonal as 100% minus the rest of the row.
