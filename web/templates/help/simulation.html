A simulation runs your whole plan many times, each time against a different simulated future of returns, crashes and inflation. Every trial goes through exactly the same year-by-year code as the fixed-return projection — a single trial is just the special case — so the two can never quietly disagree.

What one trial does

Each year, in this order: income arrives; any forced minimum distributions are taken; the withdrawal policy sets the year’s spending; tax on income is worked out; the remaining need is withdrawn from accounts in your draw order, grossed up for the tax each withdrawal triggers; any surplus is paid in; fees are charged; returns are applied; accounts set to rebalance annually are rebalanced; guardrails adjust. Everything is computed in today’s money, using that trial’s own inflation path, so a real result is correct path by path rather than deflated by an average.

A trial succeeds when no year has an unmet need — the spending the policy set for that year, plus debt payments and tax, all paid — and the final real net worth is at least your legacy target.

The dashboard menu offers 500 to 25,000 trials. The API behind it accepts anything from 100 to 50,000 and quietly clamps values outside that range.

Trials and the error bar

A success probability is estimated from a finite sample, so it has a standard error of √(p(1−p)/n), where p is the success rate and n the number of trials. The dashboard shows ± 1.96 of those — a 95% interval. That is why 82% from 200 trials is really 82% give or take about five points.

The error is largest at 50% and shrinks towards 0% and 100%. To reach ±1 point at 95% confidence you need about 1.96² × p(1−p) ÷ 0.01² trials: roughly 4,900 at 85% success and 9,600 at 50%.

If one scenario shows 84% and another 86% at 2,000 trials, you have not shown that one is better. Either run both at a much higher count, or run them on the same seed so the random draws are shared and only your change differs.

Seeds and reproducibility

The random numbers come from L’Ecuyer’s combined generator, seeded per trial and per dimension (asset shocks, regimes, crashes, inflation and so on). Three consequences follow:

  • Same seed, same inputs, same trials: same answer, on any machine, every time. Nothing is random between runs.
  • More trials add futures rather than reshuffling them. Trial 1 is identical whether you ran 500 or 25,000.
  • Switching a feature on does not reshuffle the others. Turning the crash process off leaves the asset shocks exactly where they were.

The seed lives on the household page. Keep it fixed while comparing changes; change it once, at the end, to confirm a result is not an artefact of one set of draws. {{ goto('plan_section', 'Open household', 'household') }}

The compare page runs every scenario at 1,500 trials on its own fixed seed, so its figures can differ slightly from each scenario’s dashboard.

Where results live

Results are kept in the server’s memory, one set per scenario. They are thrown away the moment you save a change to that plan, because they no longer describe it — the dashboard then shows the deterministic view until you run again. They are also lost when the server restarts. Plans themselves are in the database and are never lost this way.
