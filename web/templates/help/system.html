RetPlan keeps everything in one database — SQLite by default, PostgreSQL if you prefer — and reads its settings from one small file. This page is for whoever installs and looks after it.

The configuration file

Settings live in config/retplan.toml. Point RETPLAN_CONFIG at another file to use that instead. Every setting can also be given as an environment variable, which wins over the file:

The launcher, python run_retplan_web.py, listens on 127.0.0.1:5007; change it with --host and --port (or RETPLAN_HOST and RETPLAN_PORT). Relative paths such as data and sqlite:///data/retplan.db are relative to the directory you start RetPlan from, so start it from the project directory, or use absolute paths (sqlite:////srv/retplan/retplan.db, with four slashes). The {{ goto('system', 'system page') }} shows the file that was read and the values in effect. Settings are read once, at start-up.

SQLite or PostgreSQL

SQLite needs nothing installed: the database is one file, created on first start. It runs in write-ahead-log mode, so the background price collector never blocks a page. For one person or a household it is all you need.

PostgreSQL suits a shared server, or if you already run it and back it up. It needs the psycopg driver, installed from requirements.txt.

  • Set url = "postgresql+psycopg://user:password@host:5432/retplan" under [database], or export RETPLAN_DATABASE_URL.
  • Restart RetPlan. The tables are created from schema/postgres.sql.
  • To bring your existing data across, copy it (next section).

    The two schema files, and no migrations

    The tables are described twice, by hand: schema/sqlite.sql and schema/postgres.sql, one per database, defining the same nine tables (plans, portfolios, securities, holdings, prices, fetch_runs, projections, import_drafts, app_settings). On start-up RetPlan checks the database against the file for its dialect:

    • No RetPlan tables at all: the schema is built from the file.
    • Every table and every column present: it starts.
    • Some present, some missing: it refuses to start with a SchemaError naming the missing tables, rather than half-creating them next to data it does not understand.
    • A table missing a column the file declares (a database made by an older version): it refuses to start and names each missing column. Add them with ALTER TABLE … ADD COLUMN using the type and default in the schema file - for example ALTER TABLE securities ADD COLUMN source TEXT NOT NULL DEFAULT 'yahoo' - or start a fresh database and copy your data across.

    There is no migration tool. If a future version needs a schema change, create the missing tables from the schema file by hand, or point RetPlan at a fresh database and copy the data into it.

    Copying between databases

    python tools/copy_db.py --from sqlite:///data/retplan.db \
    --to postgresql+psycopg://retplan:secret@localhost/retplan
    • --from defaults to the configured database; --to is required. Any two supported URLs work, SQLite to SQLite included.
    • The target is built from its own schema file if empty, and must hold no rows in any RetPlan table: the tool refuses rather than merging into live data.
    • Every table is copied, parents before children, with the same ids, so the links between plans, portfolios, holdings and projections survive. On PostgreSQL the id sequences are moved past the copied ids afterwards.
    • Stop RetPlan first, so nothing changes mid-copy.

    Then point the configuration at the new database and restart.

    Plan simulation results are not stored; they are kept in memory and recomputed on demand.

    Workspaces and the session secret

    RetPlan has no user accounts. The first time a browser visits, it is given a random workspace id, kept in a signed cookie (retplan_session, valid for a year). Every plan, scenario and portfolio belongs to a workspace, and the cookie is the only key to it. The cookie never carries your finances — only the id.

    {% call note('warn', 'Clearing cookies loses the way back') %}

    A different browser, a private window, or clearing this site's cookies starts a new, empty workspace. The old workspace's plans and portfolios are still in the database, but nothing in the app can lead you back to them. Download your plans as JSON now and then — that file can be imported into any workspace.

    {% endcall %}

    The cookie is signed with a secret. If RETPLAN_SECRET is set, that is used; otherwise one is generated on first start and kept in data/.session-secret (readable only by its owner), so restarts do not log everyone out of their workspace. Deleting that file, or changing RETPLAN_SECRET, invalidates every cookie at once: every browser gets a new, empty workspace. Treat the file as part of your data.

    {% call note('trap', 'Not for the open internet as it stands') %}

    Anyone who can reach the server gets a workspace. Workspaces keep each other's plans and portfolios apart, but there is no password. Keep RetPlan on 127.0.0.1 or a trusted network, or put it behind a reverse proxy that asks for one.

    {% endcall %}

    Backing up

    • SQLite, stopped: copy data/retplan.db. If retplan.db-wal and retplan.db-shm files are beside it, copy them too.
    • SQLite, running: use SQLite's own backup, which is consistent while RetPlan writes: sqlite3 data/retplan.db ".backup backup-2026-09-29.db".
    • PostgreSQL: pg_dump retplan > retplan.sql, or whatever your server already does.
    • Always: data/.session-secret (unless you use RETPLAN_SECRET). A restored database without it is intact but every workspace is unreachable from existing browsers.

    Prices need no backup: a year of them is re-collected in one run.

    The system page and the health check

    The {{ goto('system', 'system page') }} shows the database in use (password hidden), the price collector's schedule and next run, how many closes are stored, the versions of RetPlan, Python and SQLAlchemy, the row count of every table, and the effective configuration.

    /healthz returns a small JSON document for monitoring: status (ok, or degraded if the database cannot be queried), the version, the database dialect, database_ok, and the price scheduler's status (enabled, time, whether its thread is alive, next run).
